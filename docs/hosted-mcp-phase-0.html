The Login Handshake

Before we can host anything, we need three pieces of information from the platform team. This page explains what they are, why we need them, and what happens if they don't exist.

The whole ask, in one line: we need three settings from whoever runs ArcAI's login system, so DeliveryOS can check that someone is really signed in without building a second login of our own.

01

Issuer

Who issued the pass. Lets us reject anything that didn't come from ArcAI.

02

Key list

How we check the pass is genuine and hasn't been forged or edited.

03

Audience

Which door the pass opens. Stops a pass for another system working on ours.

The idea, using a ticket

Imagine a festival wristband. Three things make it work, and they map exactly onto what we're asking for.

The box office issued it. If a wristband turns up from some other event, security rejects it. That's the issuer.

It has a hologram. Staff hold it to the light and confirm it's real rather than printed at home. They don't phone the box office each time — they know what a genuine hologram looks like. That's the key list.

It says which stage it admits you to. A wristband for the main stage doesn't get you backstage. That's the audience — and it's the one people skip, which is exactly why it matters.

Without the third one, a pass someone was given for a completely different ArcAI service would also open DeliveryOS. The audience value is what makes a pass specific to us.

What the three values look like

Roughly this shape. Illustrative — these are made-up examples to show the form, not real values. 

// 1. Issuer -- who signs the passes
https://identity.arcai.example.com

// 2. Key list -- where we check a pass is genuine
https://identity.arcai.example.com/.well-known/jwks.json

// 3. Audience -- the name that means "this pass is for DeliveryOS"
deliveryos-mcp

The good news: the first two almost certainly already exist. We found the key list endpoint in the platform's identity service while researching this. The third — a name reserved for us — is the one that may need creating, and it's a small piece of configuration rather than new software.

What actually happens when someone connects

  1. A person signs in to ArcAI as normal.

    Same login they already use. Nothing new for them to learn, and no second password.

  2. Their AI assistant connects to DeliveryOS and presents the pass.

    This happens automatically in the background. The person doesn't see it.

  3. DeliveryOS checks four things.

    Is the hologram genuine? Did ArcAI issue it? Is it meant for us? Has it expired? Any one of those failing means refusal.

  4. If it all checks out, we answer. If not, we refuse.

    There's no anonymous mode and no guest access. No valid pass, no answer.

Step 3 needs no phone call to ArcAI. We fetch the key list once and can then verify passes on our own — which means DeliveryOS keeps working even if the login service is briefly down.

What's actually inside a pass

A pass isn't just a yes or no — it carries facts about who's holding it. Opened up, one looks roughly like this. Illustrative 

{
  "iss": "https://identity.arcai.example.com",  // who issued it
  "aud": "deliveryos-mcp",                      // who it's for
  "sub": "a4f1...",                             // which person
  "tenant_id": "acme-corp",                     // which customer
  "roles": ["engineer"],                        // what they are
  "exp": 1789412400                             // when it stops working
}

That tenant_id is worth noticing. It's how one customer's people are kept separate from another's — and it arrives with the pass, so we never have to ask "who is this and what are they allowed to see?" ourselves.

Why we're asking instead of just building it

OptionWhat it costsSensible?
Use ArcAI's existing login Three settings and a small amount of code on our side Yes
Build our own login for DeliveryOS Weeks of work, plus a second set of passwords for people to manage and for us to keep secure No

ArcAI's identity service already does this properly — we checked. It handles sign-in, expiry, renewals and revocation, and it already publishes the key list we'd verify against. Rebuilding that would mean a second place for logins to go wrong, and every serious security problem in this area comes from having two systems that disagree.

If the answer is "we don't have those"

Then that is the real blocker, and it sits with the platform team rather than with us. Better to find that out this week than after we've built against an assumption.

There are two ways this could come back. If the issuer and key list exist but there's no name reserved for DeliveryOS, that's a small configuration change on their side. If the login service can't issue passes for other systems at all, that's a genuine piece of work for them — and it changes the timeline for hosting, which is something the sponsor would want to know early rather than late.

The message to send

Hi — we're adding a hosted version of DeliveryOS that AI assistants can connect to, and we'd like it to use ArcAI's existing login rather than building a separate one.

To do that we need three things:

1. The issuer URL for tokens ArcAI issues.
2. The JWKS URL, so we can verify them.
3. An audience value reserved for DeliveryOS, so a token issued for another service can't be used against ours.

If the first two already exist and only the third needs setting up, that's all we need. If issuing tokens for other services isn't supported yet, let us know — that would change our timeline and we'd rather know now.
