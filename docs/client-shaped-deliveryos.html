DeliveryOS · Findings and plan

Clients Who Aren't Us

DeliveryOS quietly assumes every client looks like we do — a git repository, and Claude. Three gaps follow from that, and none is as expensive to close as it looks.

The short version. A client who keeps their material in SharePoint cannot use DeliveryOS at all today. If they send us a link, nothing turns what is behind it into something we can read. And every document we hand a client — onboarding, proposal, delivery plan, business case — still starts from a blank page.

All three are fixable, and two of them mostly by copying something we have already done. Reading a non-git folder is three functions, because git turns out to be barely entangled. Making a client's folder usable is the same shape our own library already has, which nothing moves or copies. And the documents one is a convention plus one artifact and no product code at all — after which every new template is content somebody writes, not engineering.

Part one — not everyone uses git

The gap

A client with no git library cannot buy DeliveryOS

HR, compliance, design and ops teams keep their shared material in SharePoint, OneDrive or Google Drive. Today, adding a library is a git clone — so those teams are not a hard sell, they are simply not a customer.

What we found in the code

Git is far less woven in than it looks. It lives in one 205-line file with nine functions, imported by exactly three files. And the reading side asks git for only one thing:

Put a folder of files here, and tell me when it last changed.

Everything downstream already works on plain files and does not care where they came from:

Part of the productNeeds git?
Reading the library and its manifestsNo — plain directory listing
Knowing an artifact has a newer versionNo — compares a version number in a file
Noticing you edited an installed artifactNo — compares against its own saved copy
Detecting the source driftedNo — compares checksums
Contributing an artifact backYes, genuinely — it makes a branch and opens a pull request

The answer: read the synced folder

SharePoint, OneDrive and Drive all install a sync client that makes the content appear as an ordinary folder on the machine. So we do not integrate with three different clouds — we read a folder, and one adapter covers all three. No accounts, no API keys, nothing for the client's IT department to approve. 

> deliveryos remote add "C:/Users/priya/Acme Corp/Shared Artifacts" --name acme-shared

Added remote "acme-shared" (folder)
Found 34 artifacts.
Read that example carefully

It says "found 34 artifacts", and that quietly assumes the folder is already organised the way DeliveryOS expects. A real client's folder will not be. That is a second problem, and it is the bigger one — it has its own section below.

One limitation in the first slice

Contributing back is off to begin with, and DeliveryOS says so rather than half-working: 

> deliveryos push my-skill --remote acme-shared

"acme-shared" is a folder library. Contributing is not turned on
for these yet.

That is a choice about sequencing, not a permanent fact — the next section is about what these services can and cannot actually do when written to.

Can we push things back to them?

Worth researching properly rather than assuming, because the answer turned out better than expected in one direction and worse in another.

  Can we write? Keeps version history? Can a change be reviewed before it lands?
SharePoint Yes Yes — with who and when Approval exists, but only through their old programming interface
OneDrive (personal) Yes Yes No such thing at all
Google Drive Yes Yes, but you cannot roll back — only download an old copy and re-upload it A real approvals feature, with two catches below

The good surprise: history comes free

Writing a file into the synced folder creates a proper version in the cloud. Microsoft's own documentation treats the sync app as something that produces versions, and a new version is recorded whenever a file is uploaded or replaced.

So an artifact written into a client's SharePoint folder gets a real history entry — who changed it, when, and the ability to restore what was there before — with no accounts, no keys and nothing for their IT to approve. That is genuinely more than we get from a plain folder, and more than this plan originally assumed.

The bad surprise: you cannot gate anything

Contributing in DeliveryOS today means proposing a change that somebody reviews and accepts or rejects. Nothing here can do that honestly:

  • SharePoint does have proper approval — a document can sit as a draft that only editors see until somebody approves it. But those controls are missing from the modern programming interface and reachable only through the older one, which means a whole second way of signing in. It is also switched off by default, so most libraries could not do it without an administrator changing a setting first.
  • Google Drive has a genuine approvals feature, and its states line up neatly with what we already track. But it is only on paid tiers, and it approves the file as it already is — the change has landed before anyone looks at it. That is the opposite of proposing something while the original stays untouched.
  • Personal OneDrive has nothing.
The honest product line

You can contribute to a SharePoint or Drive library, and the change is recorded with your name against it. What nobody can offer is review before it lands — whatever checking the organisation does happens in their tools, not in ours.

A client who wants contributions reviewed and approved is a client who wants a git library. That is a real answer to give in a sales conversation, not a dodge.

The one thing we could not verify

What happens when two people change the same file. There is no current documentation from Microsoft on it — the page that used to cover it is gone. What is widely observed is that OneDrive keeps both copies and renames the loser after the computer it came from (skill-DESKTOP-A1B2C3.md). It never merges, and nobody is told.

That is the strongest argument for eventually writing through the proper programming interface rather than dropping files in the folder: it can be told "only save this if nobody else changed it since I looked" and gives a clean error instead of a silent duplicate. Same free version history, without the mystery twin.

Not needed for reading, which is the first slice. Worth knowing before we write anything.

Things that will bite, stated up front

ProblemWhat we do about it
Sync clutter. desktop.ini, ~$report.docx and .DS_Store would be read as if they were part of an artifact Fixed — ignore them, the way git files are already ignored
Files that are not really there. OneDrive can leave a placeholder that only downloads when opened — which fails offline Fixed — report it as a skipped artifact instead of crashing
Half-synced folders. Nothing stops the sync app rewriting files while we are reading them Accepted and written down. A folder library declares that it cannot promise this
Altered files. Some services quietly change line endings, which breaks our tamper checks Accepted and written down, beside the code that checks

The harder half: a folder is not a catalog

The gap

A client sends a link, not a library

Everything above answers where the files live. It does not answer the question underneath it: whatever is behind that link is a pile of documents, and DeliveryOS needs a library. Nothing in the product turns one into the other today.

What a pasted link can actually get you

Researched against Microsoft's and Google's own documentation, and the useful conclusion is a negative one: the link is a hint, not a way in.

  • There is no documented way to turn a SharePoint address into the folder on your disk. The registry keys people use for it appear in no official documentation, the sync app updates roughly fortnightly, and a company policy can rename the folder anyway.
  • But Windows will list every synced folder on the machine, properly and supported — including Google Drive's, not just Microsoft's. So the honest design is: read the names out of the link, look for a matching folder, and ask the person to confirm the match once. That turns an unavoidable guess into a single click rather than a thing that can silently be wrong.
  • Microsoft can resolve a share link directly if someone signs in — one call returns the folder and its contents. Two catches: the least-privileged permission on offer is a write permission for a read operation, and their documentation is explicit that even an "anyone with the link" link cannot be read without a signed-in user.
  • Google is the opposite, and it is the one genuinely cheap path: their documentation says a plain API key can read content shared as "anyone with the link" — no sign-in at all. If that extends to listing a folder's contents, Google onboarding becomes one sharing toggle by the client. That is a five-minute test and it is worth running before anything else.

Why the obvious tools do not close it

What you would reach forWhy it does not help
deliveryos scan It looks in six fixed places that are all Claude Code conventions, has no reader for Word, PDF or Excel, and can only look at the folder you are standing in. A client's playbooks/ folder returns nothing
Pushing each file as a new artifact It works, and it is one pull request per artifact. Two hundred files is two hundred pull requests

The answer is sitting in our own library

We have already done this once, at scale, and the shape it produced is the design. Our own library was never reorganised. The original collection still sits exactly where it was, and a thin layer of small description files was laid over the top, each one pointing back at an untouched original: 

the library/   agents/  commands/  rules/  files/   <- originals, untouched
               artifacts/                          <- the layer we added
                 230 entries, 131 of them nothing but a description
                 pointing back at:  agents/ 67   rules/ 35   commands/ 28

Nothing moves and nothing is copied. The entire footprint of making a folder DeliveryOS-compatible is one directory of small text files — a median of 527 bytes each, 132 KB for all 230, against a library of 8.8 MB. And the link is two-way: editing an adopted file and contributing it back writes to the real file, so it stays live rather than forking into a copy.

Where that layer can live — and it is not a free choice

A description file can only point at something in the same repository as itself. That single constraint decides the question:

What the client hands overWhat has to happen
A git repository Add the layer beside their files. Nothing moves, nothing is copied, and contributions still work
A SharePoint or Drive folder A copy is unavoidable — mirror the folder into a library we manage, then add the layer to that. Not a preference: a description file cannot reach into SharePoint, and SharePoint is not a git remote, so refreshing and contributing would not work there anyway
So, a rule

Never write our files into a client's SharePoint or Drive. Not merely intrusive — the rest of the product cannot work against it. DeliveryOS's job starts at "a folder inside a git repository", and getting a client's material that far stays a separate, boring step: an export, a sync, an existing tool. Teaching DeliveryOS to speak to Microsoft's and Google's services directly would be building a different product.

What can be worked out, and what has to be asked

Our own import is the evidence, and it is encouraging in one direction and clear in the other. All 210 imported entries got genuinely useful descriptions — because the source files already carried their own. But half of them ended up with an empty stack field, because nothing could work it out.

Needed for each artifactWhere it comes from
Its name, version, source, and whether review is requiredWorked out automatically
Its descriptionLifted from the file itself where the file says; otherwise best-effort and marked as a guess
What kind of thing it is, and where it should land in someone's projectGenuinely needs a person. These are the two DeliveryOS has always refused to guess

The move that makes it tractable: decide per folder, not per file

Two hundred judgement calls is where quality collapses — our own import needed two clean-up rounds afterwards, one correcting 134 files and one fixing twenty whose tags were wrong. Asking about a directory instead turns that into about eight decisions somebody can actually hold in their head: 

Agent:  There are 47 markdown files under playbooks/. Three examples:
        onboarding-call.md, escalation.md, handover.md
        What are these, and where should they land in a project?

You:    They are process rules. Put them under .claude/rules/playbooks/

Agent:  Understood. That covers 47 of the 212 files. Next: docs/templates/ ...

One answer becomes a rule that covers a whole folder. The rules are written to a file the person reads and edits before anything is committed — which also means re-running it later is safe, because new files land under the rules already agreed.

That is also the same principle as the document templates in the next section: work out what you can, ask about the rest, never invent. Two features, one rule.

One-time, not continuous

The temptation is to have this run constantly, so a document dropped in SharePoint appears automatically. The evidence says do not. Our own import was one-time with a person reviewing it and still needed two rounds of corrections. A continuous version has nobody reviewing, and the two judgement calls do not get easier by being made more often. It is the shape most likely to look like automation and behave like drift.

Part two — documents that interview you

The gap

Every document we hand a client starts from a blank page

Onboarding is the obvious one, but it is not special. Proposals, delivery plans, business cases, scoping documents — each is a document we have written many times, where the structure is always ours and only the answers change per client.

So the thing to build is not an onboarding feature. It is a shape every one of those documents follows, with onboarding as the first one through it.

The agent asks the questions, not DeliveryOS

This is the decision everything else follows from. DeliveryOS never asks anyone anything today, and it should stay that way. Instead a template declares its own questions, and one shared instruction file teaches any AI agent how to run the interview.

That is not a shortcut. It is the same decision already made once in this product and written down at the time — when we chose not to have the server ask questions directly:

"The agent is a better interviewer anyway: it already has the conversation, it can ask follow-up questions the server never anticipated, and this shape works in every client that speaks the protocol at all."

That last clause is also why it answers the other requirement: it works with Claude, Codex, Cursor or a local model, because a plain instruction file is something any of them can read.

How the pieces fit

PieceHow manyWho writes it
The method — how to interview, what never to do, where to saveOne, sharedUs, once
The templates — onboarding, proposal, delivery plan, business case…ManyAnyone. No code involved

Keeping the method in one place is the whole point. If it were copied into each template, then fixing a bad instruction — or adding a rule like "never invent an answer" — would mean editing every template we have ever written, and they would quietly drift apart. This product has been bitten by exactly that shape more than once.

What a template looks like

A template is an ordinary markdown document with its questions declared at the top. Nothing in DeliveryOS needs to understand them — the agent reads them: 

client-onboarding.md
---
document: Client onboarding
interview:
  - ask: What does the team use for chat?
    options: [Slack, Microsoft Teams, Google Chat]
  - ask: Where does documentation live?
  - ask: How does someone get access on their first day?
---

# Onboarding — [client name]

## How this team communicates
[chat tool, and what each channel is for]

## Where things live
[documentation, code, designs]

Adding a proposal template means writing one more file like that. No engineering, no release, no new concept — and a template with no interviewer installed is still just a document someone can fill in by hand, exactly like the ones we ship today.

What it looks like in use

> deliveryos pull document-interview      the method, once per project
> deliveryos pull client-onboarding       the template you need today

...then, in whichever agent you use:

You:    Run the client-onboarding interview for Acme Corp.

Agent:  What does the team use for chat — Slack, Teams,
        Google Chat, or something else?
You:    Teams.

Agent:  And where does documentation live?
You:    SharePoint, mostly. Some older stuff in Confluence.

Agent:  How does someone get access on their first day?
You:    Not sure, actually — IT handles it.

Agent:  Written ONBOARDING.md — 6 sections, 1 gap flagged
        where you weren't sure.

Two rules the method must carry

Never invent. If the client does not know, the document says so rather than filling in something plausible. We already use exactly this rule elsewhere, phrased as "never invent a URL". A proposal with a confidently wrong budget in it is worse than one with a blank.

Write the finished document to the project's own folder — not into the template's folder. This matters more than it sounds:

Why that rule exists

DeliveryOS keeps a private copy of every artifact you install, so it can tell when you have edited one — and contributing sends your edits back to the shared library. A finished document sitting in the template's folder would be treated as an edit, and could be published to a shared library with a real client's commercials in it.

The product already warns about this shape elsewhere. Nothing prevents it automatically, so the method has to state it — which is another reason it belongs in one file rather than copied into twenty.

Why this needs no new code

Two artifacts already in the library do most of it, and the new one is the small gap between them:

Already shipsWhat it does
codebase-onboardingProduces a structured guide — but reads the code for its facts
friction-logA document template with blanks, examples and instructions, filled in by a person
the methodThe first one's shape, taking its facts from a conversation — and pointed at any template

So this is a convention plus one artifact, not a change to the product. Templates after the first are content.

Where this fits the architecture

Worth answering directly, because it is the strongest argument for doing the storage work now rather than when a client finally asks.

DeliveryOS is already built this way

The design has a name — a hexagon: one engine in the middle, and everything around it plugged in through a declared interface rather than wired straight in. The architecture document says so plainly, and adds that it is not wishful thinking:

"The repository is a hexagon: one engine, and several driving adapters over it. That is not aspiration — the test suite fails the build if the newest adapter reaches past its port."

But it is lopsided, and storage is the gap

There are two sides to a hexagon: things that call in to the engine, and things the engine calls out to. Only one side is properly built:

SideWhat plugs in thereState today
Calling in The command line, the desktop app, the agent surface Well built — declared interfaces and seven tests guarding them
Calling out GitHub… and nothing else Exactly one, and no interface for storage at all

So git is not plugged in — it is wired in. Which is why supporting a second kind of library looks daunting and turns out not to be.

It clears the bar this team already set

An interface you only ever have one implementation of is usually just extra ceremony, so the team's rule is that you build one when a genuine second implementation is waiting. This is the case that rule was written for — from our own notes on the call where it was agreed:

"He named SharePoint, S3 and 'a folder somewhere' as where clients actually keep their libraries, and today only local and GitHub work. That's the one port with a real second implementation waiting — which is exactly the bar he set for when a port is worth building at all."

So this is not architecture for its own sake. It is the one case already identified by name as qualifying, by the person who set the test.

What it looks like

   the engine                     the plug              what plugs in
   (reading the library,
    updates, edits, drift)

        unchanged       ———>   "give me a    ———>   git
                                folder of files"   ———>   a synced folder
                                                    ———>   (anything later)

The engine does not change at all — and that is the evidence the seam is in the right place. Reading the library, checking for updates, spotting your edits and detecting drift already work on plain folders. They ask for a directory and read it. Nothing in them knows or cares that git put it there.

A useful side effect

Tests currently have to build real git repositories to have something to read. With a folder library they can use an ordinary directory instead — faster, and far less machinery. This team has already measured what a declared interface buys: testing the desktop side needs a 1,283-line harness that starts a real process, while the agent surface tests against a stand-in in 87 milliseconds.

Two things this deliberately does not become

The document templates get no architecture at all. They are content — a markdown file with its questions written at the top. Wrapping content in an interface would be inventing structure for something that is not code, and one reason this codebase stays workable is that it does not do that.

The command line and desktop app stay as they are. They are wired straight into the engine, and that genuinely costs something — it is why the desktop tests need that 1,283-line harness. But neither has a second implementation waiting, so neither meets the bar. "Make it all hexagonal" is how a real, narrow architectural win becomes a quarter of churn.

We are doing Claude first, as agreed. This is written down so that when a client turns up using something else, nobody rediscovers it as a surprise.

What we are deliberately not doing

  • Not integrating with Microsoft or Google directly. No app approvals, no tokens, no per-client IT conversation. The synced folder covers all three services with one adapter. Revisit only if a real client needs version history the folder cannot give.
  • Not building a template engine. The agent writes the document. DeliveryOS does not fill in blanks — adding that would create a second, competing way to configure an artifact.
  • Not building a questionnaire into the product. That is weeks of work to do worse than a conversation already does.
  • Nothing for Codex or Cursor yet.

Order of work

  1. Make a pasted link fail well. Done. Everything else here is weeks; this was a day, and it is the first thing a client-facing flow touches. Pasting a SharePoint link used to produce git's own error message; a link copied from a browser while looking at a folder was silently misread; an empty one printed a crash report; and a private link could hang forever with nothing to cancel. All five now fail with a sentence that says what to do instead.
  2. This document.
  3. The method, plus onboarding as the first template — one artifact and one template, no code, usable on the next client immediately. Proposal, delivery plan and business case follow as content whenever somebody writes them.
  4. Folder libraries — read-only, plus the honest refusal when someone tries to contribute back. This is the piece that turns a "no" into a "yes" in a sales conversation.
  5. Adoption — the layer that makes a client's folder readable at all. Start with the narrowest useful case: a repository already on GitHub, markdown only, one folder rule. The test that it worked is not "a pull request opened" but installing one of the adopted artifacts puts the original file in the right place.
  6. Other agents — when a client actually uses one.

Status: a plan, not built. The counts and the code findings were measured in the repositories; the examples are illustrative of the intended behaviour rather than transcripts of working software. The onboarding artifact needs no product changes; folder libraries do.
