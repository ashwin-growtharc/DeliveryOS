DeliveryOS · Identity

Logging In To DeliveryOS

DeliveryOS has never asked anyone to log in, and it stores no password, token or key of its own. That is not an oversight — it is what running on your own machine buys you, and git already answers the permission half. Hosting is what takes both away.

The short version. Locally, DeliveryOS doesn't authenticate you — it borrows three identities you already have. A hosted server can borrow none of them, which is the entire reason a login question exists.

If it stays local, there is no work here at all. If it is hosted, there are two ways to get a login, and they differ by about seventy-five times in size.

How DeliveryOS knows who you are today

It doesn't, directly. Every action that needs an identity reaches for one that is already on your machine. Checked in the source: DeliveryOS holds no credential of its own anywhere.

When it needs to knowWhose identity it usesWhere that comes from
Can you run it at all?Your computer loginIt runs as a child of your editor, as you
Reading the catalogYour git accessYour SSH key or git credential helper
Who authored a contributionYour git identitygit config user.name / user.email
Permission to open a pull requestYour GitHub CLI loginIt asks gh for your token, and never keeps it

This is why contributing works the way people expect. A pull request from DeliveryOS arrives from you, with your name on the commit, against repositories you already have access to. Nobody granted DeliveryOS anything — it is standing in your shoes.

It is also why there is nothing to leak. There is no DeliveryOS account, no DeliveryOS password, and no store of tokens to be stolen.

What hosting takes away

A server in a data centre has none of those three. It is not running as you. It has no git identity of yours. It has no gh login of yours. Every borrowed identity in the table above disappears at once.

So a hosted DeliveryOS has to do something it has never had to do: ask you to prove who you are. That is the whole of the work below.

The consequence people miss

Two things can never be hosted, no matter how good the login is. Contributing pushes as you, and installing writes into your working copy — and a login proves who you are without handing over your git access or your files. So hosting buys browsing. It does not buy the rest, and no amount of auth work changes that.

Who is allowed to do what

Identity and permission are different questions. The section above is who are you. This one is what may you do — and locally the answer is not "nothing enforces it", it is "something else does".

DeliveryOS has no permission system, on purpose

Checked in the source: there is no refusal anywhere based on who you are. review_required is recorded in an artifact's manifest and reported to callers, but nothing gates on it. owner is a label. Contributing opens a pull request on a branch — never a direct push.

That is not a missing feature. Git is already the access control, and it is the one the organisation actually runs on:

QuestionAnswered by
Who can see an artifactWho can clone the repository it lives in
Who can propose a changeWho can push a branch and open a pull request
Who approves itBranch protection, code owners, reviewers
Someone leaves the companyRemove them from the organisation — effective everywhere at once
Why local roles would be worse than none

The catalog is a git clone on your own disk, and the tool runs as you. Anything DeliveryOS refused, you could still do with plain git — so a local permission system would look like a control without being one. People would trust it, and it would not hold. Leaving the enforcement where it is real is the safer design, not the lazier one.

Hosting is what makes roles enforceable

A server sits between the person and the catalog, so for the first time a rule can actually be applied rather than suggested — "this team sees only these remotes", say.

On Route A that arrives largely for free: ArcAI's pass already carries the person's roles, permissions and teams, worked out fresh each time one is issued. It also refuses to issue for a deactivated account, so offboarding genuinely propagates rather than waiting for a token to expire.

On Route B it does not arrive at all — it is another 4,428 lines to port, on top of the 7,605:

Worth saying plainly: nobody has asked for roles yet. This section exists so the option is understood, not because it is needed. If hosting never happens, neither does this.

If it stays local

Then this page stops here. No login, no server, no accounts, no dependency on anyone else's identity system, and nothing to operate. All nine tools keep working, including the two that hosting could never offer.

The one thing local cannot do is serve somebody without a terminal — and that is a packaging problem, not a login problem. It is also further along than anyone has written down: npm run build:cli already produces a standalone executable, and it runs on a machine with no Node, no git and no GitHub CLI installed — verified by listing the real catalog from an empty folder with the toolchain removed from the path.

What is missing is not the build. It is a signed installer, a first-run check that says "please install Git" instead of printing a crash, and one clean machine to prove it. None of that needs a login, a server, or anyone else's identity system.

A middle option: local tool, central login

There is a third shape, and it is worth naming because it sounds like the best of both: keep DeliveryOS on people's machines, but have it log in to ArcAI anyway. Nothing is hosted, yet there is an account behind it.

The direction of the login flips. In the hosted case DeliveryOS checks passes. Here the local command line obtains one — it opens a browser, you sign in to ArcAI, and it gets a pass back for later use.

Can arc-identity do it? Yes, with two constraints

Its client records allow a client with no secret, which is the correct shape for a command-line tool. Two things it does not do, both checked:

  • No device flow. There is no "open this URL and type this code" path, so anything without a browser on the same machine cannot sign in — an SSH session, a container, a CI job.
  • Redirect addresses are matched exactly, with no allowance for a changing local port. The tool would have to claim one fixed port and have it registered in advance, which fails when something else is already using it.

What would it actually be for?

This is the part worth settling first, because three of the four plausible answers are already answered by something we have.

The hopeVerdict
Control who may run DeliveryOS Cannot work. The catalog is a git clone on the machine and the tool runs as you — the same reason local roles cannot hold
Keep some catalogs private Git already does this, and enforces it on the server where it is real
Curate the list of sources centrally Git already does this too — publish the list as a repository and let people pull it. No login, no server
See which artifacts actually get used Genuine. Git cannot answer this, and neither can we today

So of the three things hosting was going to buy, this middle path delivers one. Browsing with nothing installed still needs a hosted server; this does not provide it.

And it spends something we currently have

Today DeliveryOS stores no credential at all — it borrows the GitHub CLI's token and never keeps it. A sign-in means a token saved on disk, in every developer's home directory. "Nothing to leak" stops being true, in exchange for one answer.

Two things to settle before building it

  1. Does usage have to be per-person? Per-team or anonymous counting answers "which artifacts get used" just as well, needs no login at all, and avoids both the stored token and the question of tracking individuals.
  2. Does it need ArcAI at all? The tool already knows the git identity of whoever is running it. If that is good enough to attribute usage, the whole login disappears.

Worth being plain: this option is cheaper than hosting and buys less. It is only the right shape if usage visibility is the actual goal and the other two are not.

If it is hosted: whose front door

ArcAI has a service called arc-identity. It is the front door of a building: it checks who you are once and gives you a signed pass, and every room inside can check that pass without knowing how you were identified.

The signature can be checked offline — our server would hold no shared secret and would not call ArcAI on every request. It downloads a public key once and checks the maths itself.

It was built for exactly this case. The work is titled "OAuth 2.1 authorization server for FastMCP solutions", so that "independent solutions authenticate the same users as the ArcAI Platform."

Route A

Borrow ArcAI's front door

ArcAI issues the passes; we check them. We never see a password, never store an account, never run a login screen — which keeps the property local already has: nothing of anyone's to leak.

Route B

Build our own front door

DeliveryOS issues its own passes: our accounts, our login screen, our signing keys, our database — porting what ArcAI already has into TypeScript, because their service is Python.

How Route A works

  1. Someone adds DeliveryOS in ClaudeTheir browserThey paste our URL. No install, no terminal.
  2. Claude asks our server how to log inClaude → DeliveryOSWe answer with a small file: I don't do logins, ArcAI does. Here is where.
  3. Claude asks ArcAI where its front door isClaude → ArcAIArcAI publishes this already. We write nothing.
  4. The person logs in to ArcAITheir browser → ArcAITheir normal login. We never see the password.
  5. ArcAI hands back a signed passArcAI → ClaudeGood for ten minutes, renewed quietly.
  6. Every tool call carries the pass, and we check itClaude → DeliveryOSThis check is the only piece we write.

One function. Take a pass, return who it belongs to, or throw.

// Downloaded once, cached, refreshed automatically.
const keys = createRemoteJWKSet(new URL(`${ISSUER}/.well-known/jwks.json`));

export const arcIdentity = {
  async verifyAccessToken(token) {
    const { payload } = await jwtVerify(token, keys, {
      issuer:   ISSUER,    // who signed it
      audience: AUDIENCE,  // who it was meant for
    });
    return {
      token,
      clientId:  String(payload.client_id ?? ''),
      scopes:    String(payload.scope ?? '').split(' ').filter(Boolean),
      expiresAt: payload.exp,
      extra:     { userId: payload.sub },
    };
  },
};

What Route B actually contains

"Pull their auth code across so it's ours" sounds like copying a folder. It is a rewrite — their service is Python, ours is TypeScript — and a rewrite of security code, where the bugs are the kind somebody else finds first.

The independence is free, and it isn't in the code

Route A's hundred lines contain exactly two ArcAI-specific facts — an address and a name — and neither is written into the code: 

DELIVERYOS_OAUTH_ISSUER=<the login service>
DELIVERYOS_OAUTH_AUDIENCE=<the name reserved for us>

Point them at ArcAI and we use ArcAI. Point them at a standard login product, another team's, or our own one day, and DeliveryOS follows with no code change at all. Same check, different addresses.

So Route A is not "depending on ArcAI". It is supporting any login service, and choosing ArcAI first because the team already has accounts there. Route B buys the same freedom for 7,600 lines and custody of everyone's credentials.

The one discipline that makes this true

Those two values must be configuration from the first line written, never constants in the source. Free today; a rewrite if discovered later. It is the difference between DeliveryOS works with ArcAI and DeliveryOS is part of ArcAI.

What Route A needs from the platform team

  1. An audience name reserved for DeliveryOS. The only ask that needs something created, so worth raising first. Their own note says why: without it, "every solution in the cluster accepts every other solution's tokens."
  2. Register DeliveryOS as a client. There is no self-registration endpoint, so this is done by hand, once.
  3. Turn the feature on in whichever environment we target first.
  4. The issuer address. Everything else is derived from it.

What a login can never fix

Proving who you are is not the same as being on your machine. Six of the nine tools need the path to your project, and a hosted server has no such path.

Installing is not on that list because it is not a tool at all — it is handed over as a command for a person to run, deliberately.

So hosted and local are complements, never alternatives. A login gets a browser through the front door; it does not put the server in your shoes. Local needs no account, no server and no permission, and that is what makes DeliveryOS something you can hand to anyone.
