# Artifact retro: `arcos-cli` (Pull-only whole-repo template)

Follow-on to Phase 2 ([docs/phase-2-retro.md](phase-2-retro.md)): after Phase 2
proved the pull → edit → push → PR loop against two small ArcOS catalog
assets, a third real artifact, `arcos-cli`, was added to the same scratch
remote (`ashwin-growtharc/arc_os-catalog-poc`) to test a different shape of
artifact entirely — a `kind: template` whole-repo mirror, `review_required:
false`, Pull-only by design. This is the independent, black-box verification
of that artifact via the real, built CLI.

## What was actually tested

Using a fresh scratch `DELIVERYOS_HOME` and a fresh scratch project cwd
(neither touched by earlier Phase 0-2 manual testing):

1. `deliveryos remote add git@github.com:ashwin-growtharc/arc_os-catalog-poc.git --name arcos-poc` — succeeded first try, exit 0.
2. `deliveryos list --json` — `arcos-cli` appears correctly:
   ```
   {"id":"arcos-cli","kind":"template","version":"1.0.0","remote":"arcos-poc", ...}
   ```
   alongside `code-reviewer` and `engagement-kickoff` from Phase 2. The
   manifest itself (read after cloning, for confirmation only) shows
   `owner: senior-ai`, `version: 1.0.0`, `review_required: false`,
   `payload_path: arcos-mirror`, `post_install: pip install -e ".[dev]"`.
3. `deliveryos pull arcos-cli` — cloned the full mirror to
   `<cwd>/arcos-cli/`, ran `post_install` for real, updated the lockfile,
   exit 0.
4. Spot-checked real files landed: `arcos-cli/pyproject.toml`,
   `arcos-cli/cli/main.py`, `arcos-cli/README.md`,
   `arcos-cli/catalog/agents/code-reviewer.md` — all four present.
5. File count: the remote's `arcos-mirror/` payload has exactly 75 tracked
   files (matches the described mirror size); the pulled
   `<cwd>/arcos-cli/` directory has 81 after `post_install` runs — the
   extra 6 are `arcos.egg-info/` files generated by `pip install -e`, not
   part of the mirrored payload. Confirmed via direct diff of file lists,
   not assumed.
6. Lockfile (`.deliveryos/lock.json`) after pull:
   ```json
   { "version": 1, "entries": [ { "id": "arcos-cli", "version": "1.0.0", "remote": "arcos-poc" } ] }
   ```
   Correct id, version, and remote.
7. Directory-shape / negative check: `<cwd>/arcos-cli/` root contains
   `cli/`, `docs/`, `catalog/`, `evals/`, `mcp/`, `prompts/`, `runbooks/`,
   `pyproject.toml`, `README.md`, etc. directly at its own root — a real
   ArcOS repo layout. There is no stray extra nesting (no
   `arcos-cli/arcos-mirror/...` or `arcos-cli/artifacts/...` inside the
   pulled copy) and no collision with the scratch remote's own top-level
   `artifacts/`/`catalog/`/`README.md` (those stayed at the remote-cache
   root, never copied into the pulled artifact).

## The `payload_path` collision issue (a real, documented deviation)

The original ask implied pointing `payload_path` at the literal repo root
(`payload_path: "."`) so the mirror would read as a "real ArcOS repo
checkout." That was tried conceptually and rejected before being written
into the manifest: `arc_os-catalog-poc` is the *same* scratch remote Phase 2
already seeded with its own `catalog/`, `artifacts/`, and `README.md` at
that repo's root. Setting `payload_path: "."` would have meant `arcos-cli`'s
payload *is* the whole remote repo — including Phase 2's own
`artifacts/code-reviewer/` and `artifacts/engagement-kickoff/` manifests and
the catalog files they point at — silently pulling DeliveryOS's own
plumbing into a user's project alongside the real ArcOS files. That's not a
hypothetical edge case; it would reproduce on every single pull of this
artifact from this remote.

The fix (already reflected in the shipped manifest, verified above): the
full mirror lives in a dedicated `arcos-mirror/` subdirectory at the remote
root, sitting alongside (not overlapping with) `artifacts/` and `catalog/`.
`payload_path: arcos-mirror` then points cleanly at just the mirror, with
zero collision. This is a real deviation from the literal ask, called out
here rather than left as a silent choice: if `arcos-cli` is ever moved to
its own dedicated remote (rather than sharing a remote with Phase 2's
catalog assets), the `payload_path: "."` shortcut would become safe again —
it isn't safe on a shared remote.

## Pull-only design rationale

`review_required: false` and the complete absence of a `push` attempt in
this artifact's story is intentional, not an oversight: `push` diffs a
pulled artifact's live `install_target` against its pristine snapshot and
proposes that diff as a single PR. For a whole cloned repo, "the diff"
would be an unbounded, unreviewable blob spanning unrelated files across
`cli/`, `docs/`, `catalog/`, `evals/`, etc. — there's no single coherent
change to describe in a PR title/body, and no meaningful place upstream to
open that PR against (the mirror isn't a subtree of one real upstream path
the way `catalog/code-reviewer.md` is). The manifest's own description
field states this explicitly. This retro independently confirms the
design makes sense: nothing about how `push` works (branch + commit + PR
against `source_repo`) would produce a sane result if pointed at a 75+ file
whole-repo payload. Treating this strictly as a one-way "get me set up"
template, never proposed back, is the right call — not a gap to fix later.

## Python/pip `post_install` finding

Python and pip **are** available in this environment:
- `python --version` → `Python 3.13.12`
- `pip --version` → `pip 26.0.1 from C:\Users\AshwinB\miniconda3\Lib\site-packages\pip (python 3.13)`

`post_install: pip install -e ".[dev]"` was allowed to run for real (not
skipped). It succeeded completely: built an editable wheel for `arcos`
(`arcos==0.0.1`), installed it plus its declared dev extras (`pytest-cov`,
`ruff`, `coverage`, and already-satisfied `typer`/`rich`/`pyyaml`/`pytest`),
and the CLI reported `Pulled "arcos-cli" -> ...` with exit code 0 — no
`PostInstallError` was thrown. This is a clean, unambiguous pass: no
environment-limitation caveat needed here, unlike the placeholder concern
raised in the task brief.

## Staleness risk: `arcos-mirror/` is a point-in-time hand copy

Flagging this explicitly, with the same honesty as Phase 2's retro about
its own scratch-repo substitution: `arcos-mirror/` is a **manual, one-time
copy** of `growtharc/arc_os`'s 75 tracked files, made by hand as of this
testing session. It is not a submodule, not a subtree, not fetched live,
and has no refresh mechanism wired up beyond the manifest's declarative
`refresh: quarterly` field (which today is metadata only — nothing in the
engine currently acts on `refresh` to re-sync content automatically). The
moment `growtharc/arc_os` changes upstream — a new file, a bugfix in
`cli/main.py`, a dependency bump in `pyproject.toml` — this mirror silently
drifts out of date with no signal to anyone pulling `arcos-cli` that
they're getting stale content. Anyone relying on this artifact for a real
onboarding flow should treat it as "ArcOS as of 2026-07-24," not "ArcOS,
live," until a real sync mechanism exists (Phase 5's drift-detection work is
the natural home for that, per PLAN.md).

## What was harder than expected

Nothing about the DeliveryOS engine itself was harder than expected — the
existing `payload_path` mechanism (added during Phase 2) handled this
whole-repo case with zero further engine changes; see confirmation below.
The one genuine wrinkle was the collision issue described above, which was
a manifest/content design decision, not a code fix.

## Engine changes required: none

Zero `src/`/`test/` diffs were needed for this artifact. `git status` /
`git diff --stat` on the engine directories are clean; this was a pure
manifest + mirrored-content addition on the remote side, exercising
existing Phase 0-2 mechanisms (`payload_path`, `post_install`, the
lockfile) exactly as built.
