DeliveryOS · Client storage

Reaching a Client's SharePoint

A client's material is in SharePoint and they send you a link. There are two ways DeliveryOS can get at it, and they differ by about a month of work.

The short version. The link cannot be fetched — nothing reads its contents without somebody signed in. It can still be read, and DeliveryOS now says exactly what a link points at and what to do about it. Getting at the contents leaves two real routes: let the sync app put the files on a disk, which works today and needs no code at all, or ask Microsoft for them directly, which needs a sign-in system we do not have.

The first one does not work everywhere, and the last section says exactly where it stops.

Why the link alone never works

A SharePoint link opens in a browser because the browser already knows who you are. A program has no such session. Microsoft's own documentation is blunt about it: their interface "always requires authentication and can't be used to access anonymously shared content without a user context."

Tried against a real link, that is a flat refusal: 

fetching https://growtharc-my.sharepoint.com/:w:/p/...
HTTP 403 Forbidden

So "just read the link" is not one of the options. Both routes below are about getting past that, in very different ways.

What the link does tell you

It cannot be fetched — but it is not opaque. Microsoft puts a type marker in the first path segment, and the browser form carries the file's own name in the query string. Both are ordinary text, so DeliveryOS can say what you are holding without anybody signing in to anything.

Part of the linkWhat it says
:x: An Excel workbook. :w: Word, :p: PowerPoint, :f: a folder
…-my.sharepoint.com Somebody's personal OneDrive, not a team site
/personal/rina_patel_contoso_com/ Whose it is
file=Build%20Time%20Line.xlsx The file's name, in the clear

Not every link is that generous. The short sharing form — /:w:/p/rina_patel/IQBJ… — gives the type and the owner and no name at all. So DeliveryOS reports the name it found, or none, and never invents one.

The distinction that changes the advice

A folder link can become a catalog. A document link cannot — ever. A catalog is a folder of files, so a link to one spreadsheet has nothing in it to read, and that stays true once the file is sitting on the disk. The old message sent people off to sync a library, which does not help, because the problem was never where the file was. 

> deliveryos remote add "https://…-my.sharepoint.com/:x:/r/personal/…"

That link points at a single file, "SLM Build time Line.xlsx" in
vaishak_bhuvan_growtharc_com's OneDrive, not at a library.
A catalog is a folder of files, so there is nothing here for
DeliveryOS to read -- and that stays true once the file is on this
machine. Open the link, choose "Add shortcut to My files", and let
OneDrive finish syncing, then point DeliveryOS at the FOLDER that
document sits in.

One more branch worth knowing about: a team library gets told to hit "Sync", and a document in somebody else's OneDrive gets told "Add shortcut to My files", because the Sync button is not there. Sending a person to look for a button that does not exist is its own kind of failure.

Route A — let the sync app do it

Works today · no code

The files land on a disk, and DeliveryOS reads the folder

SharePoint, OneDrive and Google Drive all have a sync app that makes their content appear as an ordinary folder. DeliveryOS does not integrate with three clouds — it reads a folder, and the same code covers all three.

  1. Paste the link Person · five seconds

    Whatever the client sent, exactly as they sent it.

    Behind The host is matched against a short list of things that cannot be git. Then the link is read: the type marker, the owner, and the file name if the link carries one. No network call, no sign-in.
  2. DeliveryOS says what the link is, and what to do about it DeliveryOS · immediately

    Named file, named owner, and one instruction that fits this link rather than all links.

    Behind The refusal is a value, not an error — so the wording is unit-tested directly. It branches twice: folder or document, then personal OneDrive or team library, which is what decides between "Add shortcut to My files" and "Sync".
  3. Someone who already has access syncs the library Person · once, in their browser

    It then appears in their file explorer like any other folder. This is the only step that needs a human, and it needs one exactly once.

    Behind — nothing, deliberately DeliveryOS is not involved. The sync app writes the tree to disk under that person's own account, which is why no keys and no IT approval are needed anywhere in this flow.
  4. Point DeliveryOS at the folder Person · one command

    An ordinary path. The same command a git URL would use.

    Behind Which kind of remote this is gets decided by asking the filesystem, not by pattern-matching the text. The remote is recorded as a folder library, and that carries its own honest limits — reading and installing work, proposing a change does not.
  5. Mirror and adopt Person · once per client

    A pile of documents becomes a library DeliveryOS can read.

    Behind The tree is copied into a catalog we manage, dropping the sync app's leavings (desktop.ini, ~$…, .DS_Store) so they never become somebody's artifacts. Each file gets an id and a description read from the file itself — a Word, Excel or PowerPoint file is opened up and asked for its declared properties, then its first line of text. Nothing is invented; a file that cannot describe itself is reported, not guessed at.
  6. Review one pull request Person · once

    One change, listing every proposed artifact and flagging which descriptions were derived rather than declared.

    Behind Every manifest is checked before any of them is committed, and one failure aborts the whole batch. That is not caution for its own sake: a single malformed manifest makes the entire catalog unreadable, so it lands all at once or not at all.
  7. Anyone installs an artifact Person · whenever

    The client's own document, in their project, where the rule said it goes.

    Behind The original is copied byte for byte, and a pristine copy is kept so later edits can be told apart from the original. Nothing was converted at any point — the .docx that lands is the .docx they wrote.
Where the writing happens

Nothing is ever written into the client's SharePoint. The pull request in step 6 goes to a catalog we manage. Their library is read and left alone — which is also why a folder remote cannot accept a proposed change: there is nowhere for a proposal to sit while the original stays untouched. 

> deliveryos remote add "C:/Users/priya/Contoso Ltd/Delivery Playbooks" --name contoso

Added remote "contoso"
This is a folder library: reading and installing work,
contributing back does not.

And step 5, first as a rehearsal. The profile is a short YAML file saying, per folder, what the files are and where they should install — the two things nothing can read off the files themselves. 

> deliveryos adopt "C:/Users/priya/Contoso Ltd/Delivery Playbooks" --profile contoso.yaml --dry-run

Would adopt 3 artifact(s) from "Delivery Playbooks" into "contoso-catalog", copying 3 file(s):

  playbook-escalation  rule  playbooks/escalation.md -> .claude/rules/playbooks/escalation.md
  playbook-handover    rule  playbooks/handover.md   -> .claude/rules/playbooks/handover.md  (description derived)
  template-proposal    doc   templates/proposal.docx -> templates/proposal.docx

1 description(s) would be derived from the file's first heading rather than
declared -- worth reading before you open the pull request:
  - playbook-handover: "Handover checklist"

Nothing was written. Drop --dry-run to open the pull request.
The thing worth noticing

This asks nothing of the client that the link did not already ask. Somebody has to have access either way. This route just does not spend a month of engineering re-acquiring access that person already has.

Route B — ask Microsoft directly

Real work · needs a sign-in

DeliveryOS holds a sign-in and fetches the content itself

Microsoft has an interface built for exactly this: give it the link, get back the folder and everything in it. The mechanics are genuinely simple. The cost is everything around them.

You scramble the link into a safe form, and ask for it: 

# the link, encoded and prefixed with u!
GET /shares/u!aHR0cHM6Ly9ncm93dGhhcmMtbXkuc2hhcmVwb2ludC5jb20v.../driveItem?$expand=children

# comes back with the folder AND its contents, in one call
{ "name": "Delivery Playbooks",
  "folder": { "childCount": 12 },
  "children": [ { "name": "Proposal Template.docx" }, ... ] }

There is even a polite mode that peeks at a link without permanently claiming access to it. So the reading part is easy.

What it actually costs

What is neededWhy it is not small
A sign-in system DeliveryOS holds no accounts or passwords today, deliberately. This adds all of it: signing in, storing the pass, renewing it, and handling it expiring at a bad moment
Registering with each client Someone in their organisation has to approve our app before it can read anything
A write permission, to do a read The least-powerful permission Microsoft offers for this is one that includes changing files. An awkward thing to ask for, on a tool that only reads
Google separately None of this transfers. Google is a second integration with its own approvals

Will route A work everywhere? No — here is where it stops

This is the honest limit, and it is worth knowing before promising anything. The sync app is a person's computer, and everything follows from that.

SituationDoes the sync route work?
Windows 10 (22H2) or Windows 11Yes
macOS 14.4 or newerYes
LinuxNo — Microsoft lists no Linux version at all
Older macOS, or Windows 10 before 22H2No longer supported
A server, a build machine, anything unattendedNo. There is nobody to click "sync"
A locked-down laptop where IT blocks the sync appNo
A very large libraryMicrosoft recommends staying under 300,000 items
Files not downloaded yet ("online only")Partly — those files are skipped and reported, rather than breaking the run
The one that matters most

Route A cannot run unattended. It needs a person, on a supported computer, who has already synced the library. That is completely fine for a consultant adopting a client's material once — and it rules out anything automatic, scheduled or server-side, forever.

If DeliveryOS ever needs to pick up a client's changes overnight with nobody watching, that is the day route B stops being optional.

A small thing that validates the approach

DeliveryOS filters out the debris a sync app leaves behind — desktop.ini, and the ~$ files Word creates while a document is open. It turns out Microsoft lists those exact names among the filenames SharePoint refuses to store. So they are noise by Microsoft's own definition, not just by ours.

What to do

  1. Use route A. It works today, end to end, including Word, Excel and PowerPoint templates. It asks nothing of a client's IT department, which is a genuine advantage in a sales conversation rather than a compromise.
  2. Know the two triggers for route B, so nobody is surprised by them: a client who will not let anyone sync their library, or a need to pick up changes with no person involved.
  3. Do not build route B on speculation. It is a sign-in system, a per-client approval and a second integration for Google — and it buys only "no sync app on the consultant's machine" until one of those triggers actually happens.

Status: route A is built and working. Route B is not built. The Microsoft limits quoted here — supported systems, the 300,000-item guidance, the prohibited filenames and the authentication requirement — were read from Microsoft's own documentation; the 403 was a real request against a real link.
