DeliveryOS · Selling it

Making Sure They Paid

We sell DeliveryOS to a company. An employee sends the installer to a friend at a different company. What already stops him, what doesn't, and the three things we could build about it.

The short version. The friend cannot reach the customer's artifacts — that already works. What he can do is use DeliveryOS with his own library, for free. So this is about revenue, not safety.

A signed licence file does not fix it, because a file can be copied along with the installer. A sign-in does, because there is nothing to copy. And there is a third answer that avoids the fight entirely.

What the friend can and cannot do

Already handled

He cannot see the customer's artifacts

The installer is not a key. It is an empty program until you point it at a library, and every library is a private repository: 

> deliveryos remote add https://github.com/acme-corp/artifacts.git

remote: Repository not found.
fatal: could not read from remote repository.

DeliveryOS holds no passwords or keys of its own — it asks the machine it is running on, and that machine has no permission either. The copy of the program grants nothing.

The actual leak

He can use it with his own library

He points it at his own company's repository and everything works. Full product, no payment. He never touched Acme's data — which is precisely why this is a billing question and not a security one.

The words, in plain terms

Entitlement
Just: is this copy allowed to be used? Nothing about who a person is — only whether this installation was paid for.
Seat
One person. "25 seats" means the customer paid for 25 people. Counting seats is the main practical reason to know who is signing in.
Revocation
Taking access back — someone left, or the customer stopped paying. A file cannot be recalled. An account can.
Federation
Letting people sign in with the work account they already have, instead of making them create a new one with us.

Two rules that shape everything

Rule one

A program on someone else's computer cannot be made impossible to run. Any check inside it can be found and removed. This is true of every product ever sold this way. The goal is not casually shareable, not uncrackable.

Rule two — specific to this product

DeliveryOS has nothing we could withhold. Search runs on the user's machine, previews compile from libraries bundled into the app, the AI features use the customer's own account, and the library is the customer's own repository. There is no piece of the product that only works if we send something.

That matters: it means every option below is a check that could be removed, not a dependency that cannot be faked — unless we change what we are selling, which is option two.

Where a check would go

Not at startup. DeliveryOS with no library is an empty window — the moment it becomes useful is when someone adds one: 

> deliveryos remote add https://github.com/his-company/artifacts.git
This copy of DeliveryOS is not licensed.
Ask your administrator, or visit deliveryos.com/activate

Once per library rather than every launch, so it barely touches people who paid; and it fails exactly where the value would have started.

Option one — sign in

Recommended

People sign in with their work account

No file to hand out and nothing to copy. The friend cannot sign in, because he does not have an account at the customer.

  1. They open DeliveryOS and sign inThe same work login they use for email. Nothing new to remember.
  2. We check they belong to a paying customerOne question, to a small service of ours.
  3. It hands back a pass that lasts a whileStored on their machine and renewed quietly in the background.
  4. Adding a library checks the passThe friend never gets one, so he never gets past this step.

Why this restricts where a file does not

A licence file is a thing you have; it travels with a copy. A sign-in is a thing you are, checked against a directory the friend is not in. To get around it he would have to modify the program itself — a completely different bar from copying a folder, and one a friend borrowing a tool will not cross.

What it costs

  • A small service, always up. It holds no libraries and no customer files — it answers one question — but somebody runs it, and it sits on the path of starting work.
  • Offline stops being free. DeliveryOS works on a plane today. With a sign-in it works offline only while the pass is valid.
  • It stores a credential on every machine. Today the product stores none at all.
  • Each customer has their own sign-in system — Microsoft, Google, Okta. Connecting to each is real work, and some providers charge per connection.

Products this size usually land between a week and a fortnight.

Option two — sell the part that cannot be copied

The one that avoids the fight

Give away the tool, charge for the service

If the program cannot be locked, stop trying to lock it. Charge instead for the things a copied installer cannot give anyone.

This is how most tools of this kind actually work. The client is free; the service around it is the product. Nobody tries to stop you running the client, because running it is not what they sell.

What DeliveryOS could sell on those terms:

What we sellWhy a copied installer cannot get it
A hosted, searchable libraryIt runs on our machine. No account, no access
Curation — a maintained collection worth havingIt is our work, not our software
Hosting libraries for companies without gitWe hold the files. This also removes a real sales objection
Support and onboardingPeople, not code
What this changes elsewhere

Every previous conclusion treated hosting as a cost — a server somebody has to run at 2am for no revenue. If hosting is the product, that calculation inverts. It stops being overhead and becomes the thing being paid for.

This is a business decision rather than an engineering one, which is why it is not a recommendation here. But it is the only option where enforcement stops being a losing arms race.

Option three — a licence file

Stopgap only

A signed file we give each customer

Worth being blunt: this does not restrict anything. Copy the file with the installer and it works. 

deliveryos.licence
{
  "licensedTo": "Acme Corp",
  "seats": 25,
  "expires": "2027-03-31",
  "signature": "MEUCIQD…"   <- only we can produce this
}

What it does buy is a legal lever rather than a technical one. The friend's copy runs visibly under Acme Corp's name, which makes misuse obvious and provable instead of invisible. And it needs no server, works offline forever, and takes days rather than weeks.

Reasonable as the thing in the first release we hand a paying company — and honest only if nobody claims it prevents use.

What the code says about building this

The checks were made against the current source. The shape of the product happens to make this cheap, which is not always true.

What we would needWhat already exists
One place to gate Adding a library goes through a single engine function, called from exactly three places — one per surface. One gate covers all of them
To declare which operations need a licence All 43 operations are already declared in one file with per-operation flags, and 11 tests force every surface to agree. A new flag follows the existing pattern
A clean way to refuse A typed error family already exists and every surface already renders it properly — including one for a failed GitHub login, which is the same shape
Somewhere to keep the pass There is already a global settings folder, holding the list of libraries
Credential storageNone — the product deliberately stores nothing today
A sign-in screenNone
A service to askNone. No hosting of any kind exists yet

Two different jobs — keep them apart

JobQuestionWho handles it
AccessMay this person see Acme's artifacts?Already solved — the repository decides, on their server, where it is real
EntitlementWas this copy paid for?New, and separate

Access already works, and it is what makes the shared-installer story end harmlessly. Do not rebuild it, do not route it through the sign-in, and do not let one system answer both. Merging them is how products end up with a login that protects nothing and irritates everyone.

What to do, in order

  1. Decide option two first, because it changes everything else. If the service is the product, enforcement stops mattering and most of this page becomes unnecessary.
  2. Put the check behind one small interface now, whichever way that decision goes. One function answering "is this copy paid for?" costs almost nothing today and makes every later choice a substitution rather than a rewrite.
  3. Ship the licence file with the first paid release — days of work, no server — while being clear internally that it deters rather than prevents.
  4. Move to sign-in at the second customer, where counting seats and cutting off leavers starts to matter more than simplicity.
  5. Never chase uncrackable. It breaks honest customers who change laptops, and delays a determined person by an afternoon.

Status: a proposal, not a commitment. There is no licensing, entitlement or credential code in DeliveryOS today, and no hosting of any kind. What the friend can and cannot do was checked in the current source; the integration points above were counted in it. Everything else is a design.
