Borrowing ArcAI's Front Door

If DeliveryOS uses ArcAI's login, does DeliveryOS become part of ArcAI? It's the right question to ask before we build, because this kind of tie is much easier to make than to undo.

Short answer: only if we build it that way. The login standard we'd be using is an open one that every major identity system speaks. Pointing it at ArcAI is a setting, not a marriage — provided we treat it as a setting from day one. If we hard-code ArcAI instead, then yes, DeliveryOS becomes an ArcAI product and stops working without it.

Where DeliveryOS stands today

Worth being precise about this, because it's the thing we'd be giving up. DeliveryOS currently has no connection to ArcAI at all. It runs on your laptop, uses your own GitHub login, reads from git repositories you choose, and installs into your own project. There is no account, no server, and nothing to sign up for.

That independence is worth something. It means DeliveryOS can be handed to a client, used on a project that has nothing to do with ArcAI, or open-sourced — without a conversation about accounts.

Before and after

Today — running locally

  • Runs on the developer's own machine
  • Signs in with their existing GitHub account
  • No server, no accounts, nothing to operate
  • Works for anyone, anywhere, with no permission needed
  • Nothing to keep running at 2am

After — hosted, with ArcAI login

  • Browsing runs on a server your team operates
  • Signing in needs an ArcAI account
  • If ArcAI's login is down, hosted browsing is down
  • New users need someone to grant them access
  • Local use is completely unchanged

That last line matters more than it looks. The laptop version keeps working exactly as it does now, with GitHub and no ArcAI account. Only the hosted browsing version gains a login requirement. We would be adding a second way in, not replacing the first.

Why the three settings aren't ArcAI-specific

This is the part that decides the whole question. The three values we'd ask for are not an ArcAI invention — they're the standard way any system proves who someone is. Microsoft, Google, Okta, Auth0 and every corporate login system publishes the same three things.

So the difference between "part of ArcAI" and "works with ArcAI" is this:

Hard-wired avoid

ArcAI's addresses written directly into our code.

// baked in
issuer = "identity.arcai.com"

DeliveryOS now requires ArcAI. It cannot be used by anyone without an account, and it cannot be given to a client on its own.

Configured

The addresses are settings, and ArcAI is what we happen to set them to.

// supplied at run time
issuer = env.OIDC_ISSUER

DeliveryOS works with ArcAI, or a client's own login, or anything else standard. Swapping is a configuration change, not a rewrite.

Both cost the same to build. The second one is simply the version where we can change our mind later. Illustrative — the code above is simplified to show the shape of the difference.

What's required

From the platform team — three values, and nothing else:

  • Issuer — the address that signs their logins.
  • Key list — where we check a login is genuine.
  • Audience — a name reserved for DeliveryOS, so a login meant for another system doesn't work on ours. This is the one that may need creating.

From us — small, and mostly already provided:

  • Turn on the HTTP connection. Our toolkit already ships it. Close to free.
  • Check the login on each request. Roughly a hundred lines. The platform team's own estimate for the same piece was the same.
  • Make three tools work without a project folder, since a server has no "your folder". Small.
  • Keep the addresses as settings, never written into the code. Free — but only if decided now.

The cost nobody has named yet is the last one: somebody has to run this server, keep it patched, and answer for it when it breaks. That is ongoing, it is not code, and it does not appear on any estimate so far.

The ties worth going in with your eyes open about

Even done the careful way, hosting creates real dependencies. None of these are reasons not to do it — they're things to have said out loud first.

Their uptime becomes our uptime. If ArcAI's login is down, nobody can browse the hosted library. Local use keeps working, which limits the damage, but the hosted version inherits someone else's reliability.

Their roadmap touches ours. If they change how logins work, we change with them, on their schedule rather than ours.

Support questions get harder. "I can't sign in" stops being a question we can answer alone.

Access becomes someone's job. Today anyone can use DeliveryOS. Hosted, somebody has to grant people access — and remove it when they leave.

The recommendation

Do it, but keep the addresses as settings. Point them at ArcAI because that's what the team already uses and it saves genuinely hard work. Never write those addresses into the code.

That single discipline is the difference between DeliveryOS works with ArcAI and DeliveryOS is part of ArcAI — and it costs nothing extra, as long as it's decided before the first line is written rather than discovered afterwards.

And keep the local version first-class. It needs no account, no server and no permission, and that is what makes DeliveryOS something you can hand to anyone. Hosting should be a second door into the same building, never a replacement for the one that already works.
